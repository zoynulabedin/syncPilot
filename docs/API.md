# SyncPilot application contracts

These are the implemented React Router loaders and form actions. The `/api/...` paths in the master specification are design proposals; this release does not expose a generic token-bearing GraphQL proxy or a second public REST API.

All `/app` loaders and actions first call the official Shopify `authenticate.admin(request)`, then consume the verified shop's and user's request budgets. Authenticated data is scoped to the current shop, or to an active workspace and verified two-store pair. Management actions additionally require a verified Shopify store owner; a few read-only preparation actions also accept `OPERATOR` staff. Actions use server-side services; hiding a button is not the authorization check.

## Browser contract

Catalog and inventory selectors use the `store` query/form field. Shopify’s reserved `shop` parameter remains authentication context and is never a business-data selector.

Actions accept URL-encoded form data. The `intent` field selects an operation. The action form parser bounds request bodies to 64 KiB and rejects other form encodings and an explicitly foreign `Origin`. Shopify authentication remains mandatory. Do not send credentials, Shopify tokens, or arbitrary GraphQL in form fields.

Successful actions return a small success message and revalidate loader data. Expected validation and authorization failures return a 4xx response containing a human-readable `error`; unexpected server failures return a generic message. Auth redirects and Shopify boundary responses retain their framework behavior. Zod validates service inputs independently of UI form parsing.

## Request limits

Budgets are counted per minute in PostgreSQL, only after Shopify authentication succeeds. Admin requests: per verified shop 600 reads (GET/HEAD) and 120 writes, per verified user 180 reads and 30 writes; parent and child loaders of one request count once. Webhooks: `products/create`, `products/update`, `products/delete` and `inventory_levels/update` share 1,200 per minute per shop (`RATE_LIMITS` in `app/services/rate-limit.server.ts`). Lifecycle and compliance webhooks and `/auth/login` are not limited. Over budget: `429` with `Retry-After: 60` and `Cache-Control: no-store`. Limiter database failure: `503` with `Retry-After: 10`. Per-IP limits are the reverse proxy's responsibility.

## Pairing and membership

`requireActor(auth)` derives `{shop, userId, role}` from the authenticated Shopify session. `OWNER` requires `onlineAccessInfo.associated_user.account_owner === true` and its associated user ID. A session-token subject or a stored boolean alone cannot grant owner authority. Other users are staff and require an explicit active workspace membership, which exists only inside an active verified pair. The membership role is `VIEWER` (read-only) or `OPERATOR` (can also call `importCatalog`, `previewPolicy` and `requestReconciliation` through `requireOperator`). `canOperate` is true for owners and for active `OPERATOR` members of a verified pair; staff on an unpaired store get read-only pages, never an error. Owners can grant or revoke staff membership; the application cannot manufacture or revoke Shopify store-owner authority.

1. `initiatePairing(actor, {destinationShop, organizationConfirmed: true})` requires both active installations, a different destination, neither store already paired, and no current pending request involving either store. Returns `{request, challenge}`. Only a SHA-256 hash is stored; the plaintext challenge is returned once.
2. `acceptPairing(actor, {requestId, challenge, organizationConfirmed: true})` runs only in the named destination installation. A bad code increments durable attempt count. Five failures lock the request. Requests expire after 15 minutes.
3. `confirmPairing(actor, {requestId})` runs only in the initiating installation, by its original verified owner. It requires the destination owner's acceptance and creates the workspace, two owner memberships and verified pair atomically.
4. `rejectPairing(actor, requestId)` cancels/rejects a pending request from either named store. Completed requests cannot be replayed.
5. `disconnectStore(actor, shop)` revokes the workspace pair and memberships, pauses policies, revokes ACTIVE and HELD automatic consents (reason `STORES_DISCONNECTED`), cancels pending/running work, revokes pending and approved plans and unlinks both connections in one transaction. Audit records remain.

State progression is `PENDING → ACCEPTED → VERIFIED`; cancellation and rejection terminate the request. Expiry is enforced on server-side state transitions even if an older persisted row still has a pending state.

Organization eligibility is attested by both owners. No Admin API organization-ownership verification is claimed. Production activation still requires documented confirmation that the stores are eligible for this custom app.

`setMember(actor, {shopDomain, userId, role: "VIEWER" | "OPERATOR", status: "ACTIVE" | "REVOKED"})` validates a paired shop and numeric Shopify staff ID. Only the owner of that shop can manage its staff. Store-owner rows cannot be demoted or modified through this interface. A transferred store should disconnect and re-pair to establish the new owners' approval proofs.

## Mapping and policies

`saveMapping(actor, {kind, sourceShop, targetShop, sourceGid, targetGid})` accepts `PRODUCT`, `VARIANT` or `LOCATION`. Both identities must be imported. Shopify GID resource types are checked. Variant verification requires a verified parent-product mapping; location verification requires both locations active. Mapping never relies on SKU alone. Unique source and destination constraints reject ambiguous destination reuse.

`deleteMapping(actor, {kind, id})` scopes the lookup by workspace. Mapping changes invalidate old pending/approved plans, revoke the workspace's automatic consents (reason `CONFIGURATION_CHANGED`) and cancel queued write and automatic preview jobs. The worker also checks mappings before each resource write, and holds variant mappings that no longer have a valid parent-product mapping.

`savePolicy(actor, input)` accepts:

| Field                      | Rules                                                                                                                                                                                          |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                       | Optional existing policy ID in this workspace; enabled policies must first be paused                                                                                                           |
| `sourceShop`, `targetShop` | Different active stores in the verified pair                                                                                                                                                   |
| `fields`                   | Any selection of `title`, `descriptionHtml`, `vendor`, `productType`, `status`, `handle`, `tags`, `seoTitle`, `seoDescription`, `price`, `compareAtPrice`, `sku`, `taxable`, `inventoryPolicy` |
| `syncInventory`            | Boolean; false by default                                                                                                                                                                      |
| `inventoryMode`            | `DISABLED` or `SOURCE`; inventory requires `SOURCE`                                                                                                                                            |
| `inventoryAuthority`       | Must equal `sourceShop` for inventory synchronization                                                                                                                                          |
| `buffer`                   | Integer from 0 through 1,000,000                                                                                                                                                               |
| `reconciliationMinutes`    | Integer from 5 through 10,080                                                                                                                                                                  |

At least one field or inventory must be selected. Opposing policies cannot own the same field or both own inventory. Bidirectional product ownership therefore uses two one-way policies with disjoint fields. Saving sets `DRAFT`, disables the policy, invalidates prior approvals and revokes the policy's automatic consents. Inventory shared-pool allocation is not an available mode.

## Preview, activation and approved execution

`previewPolicy(actor, policyId)` authorizes both stores and persists exact changes, source/target hashes, creator and 15-minute expiry. Owners and `OPERATOR` staff may call it. Previewing never writes to Shopify. Plans can contain `PRODUCT`, `PRICE`, `VARIANT`, `INVENTORY` changes or `HOLD` findings. Unknown, held, empty or more-than-1,000-change plans cannot be approved.

`updatePolicy(actor, policyId, "ACTIVATE")` requires a fresh nonempty dry run, no held items, no opposing ownership conflict and enabled deployment switches. It revokes that policy's ACTIVE and HELD automatic consents (reason `POLICY_ACTIVATED`) and cancels jobs bound to them; manual `APPLY_PREVIEW` jobs are untouched. `PAUSE` cancels associated queued/running work, revokes approved plans and revokes the policy's consents (reason `POLICY_PAUSED`). Activation alone does not authorize arbitrary future mutations.

`approvePreview(actor, previewId)` rebuilds the comparison and requires matching source/target hashes and canonicalized exact changes. A serializable transaction consumes a pending, unexpired plan once, verifies the active policy and current workspace, records the owner, and creates `APPLY_PREVIEW` with stable key `preview:<plan-id>`. Concurrent approvals yield one durable job.

The deployment variables `SYNC_WRITE_ENABLED` and `INVENTORY_WRITE_ENABLED` must equal the lowercase string `true`; inventory requires both. They are off by default. Services and workers independently enforce these switches. Enabling a switch does not skip pairing, mapping, policy or exact-plan approval.

The worker fetches current Shopify state, compares the exact approved plan again, and rechecks authorization before resource writes. Product fields use targeted updates; variant prices and selected SKU/taxability/inventory-policy fields use targeted variant updates; inventory uses available quantity, explicit location mapping, Shopify compare-and-set and a stable idempotency key. Destructive product creation/deletion, media/options/metafields and shared-pool inventory are unsupported and must remain held.

## Automatic consent

Implemented in `app/services/automatic-sync.server.ts`; bounds in `app/domain/automatic-limits.ts`. Granting and scheduling require `AUTOMATIC_SYNC_ENABLED` and `SYNC_WRITE_ENABLED` both exactly `true`.

`getAutomaticConsents(actor)` returns the latest 100 consents, every policy with an `eligible` flag, up to 100 fresh `PENDING`/`APPLIED` plans of eligible policies (no usability filter) and the switch state. The page offers only plans with 1–100 changes, all to product fields the policy owns; the grant re-validates the chosen plan. An unpaired store returns an empty, unpaired page; an inactive installation gets `INSTALLATION_INACTIVE`.

`grantAutomaticConsent(actor, {policyId, previewId, durationMinutes, intervalMinutes, maxJobs, maxChanges, perRunChanges, confirmed: true})` is owner-only and requires an active owner membership. The policy must be enabled, `ACTIVE`, owner-approved, `ONE_WAY`, product-only (no inventory, price or variant sync) and own only `title`, `descriptionHtml`, `vendor`, `productType`, `tags`, `seoTitle`, `seoDescription`; every product mapping must be verified. The plan must be a fresh exact plan with 1–100 changes, no held items and only owned fields; it is rebuilt and compared before storing. Bounds (whole numbers): `durationMinutes` and `intervalMinutes` 5–1,440, `maxJobs` 1–100, `maxChanges` 1–1,000, `perRunChanges` 1–100, and the plan must fit both change limits. Refusals include `CONSENT_SCOPE`, `MAPPING_MISSING`, `CONSENT_BUDGET`, `PREVIEW_REQUIRED`, `STALE_PREVIEW`/`PREVIEW_STALE`, `PREVIEW_EXPIRED`, `CONSENT_CHANGED`, `CONSENT_EXISTS` (one ACTIVE consent per policy; HELD does not block) and `AUTOMATIC_DISABLED`/`WRITES_DISABLED`. The route returns `SyncError` refusals, which carry no HTTP status, as 409 with their fixed message; other errors keep their own status. Audit: `AUTOMATIC_CONSENT_GRANTED`.

`revokeAutomaticConsent(actor, id)` is owner-only, works with the switch off, cancels the consent's pending, retrying and running jobs (`lastError: AUTOMATIC_CONSENT_REVOKED`) and writes `AUTOMATIC_CONSENT_REVOKED` with no `details` (no reason). The page offers it on ACTIVE and HELD consents; the service also accepts, and re-stamps, an already REVOKED or EXPIRED one.

`scheduleAutomaticSync()` (worker stage `AUTOMATIC_SYNC`, run about once a minute per worker process) expires consents past `expiresAt`, then takes up to 25 due ACTIVE consents per pass, oldest `nextRunAt` first, and always advances each one's `nextRunAt`. An exhausted consent is parked until expiry; a policy that is paused, not active, deleted or has an `AUTO_PREVIEW`/`APPLY_PREVIEW` job pending, retrying or running is skipped for one interval. Otherwise it queues `AUTO_PREVIEW` with key `automatic:<consentId>:<nextRunAt ms>`. That job either holds the consent (`AUTOMATIC_CONSENT_HELD` with `details.code` `CONSENT_BUDGET` or `CONSENT_SCOPE`, for a run over budget or outside the consented fields; or `CONSENT_CHANGED`, after which the run dead-letters, as a fallback for a consent an earlier release left ACTIVE after a configuration change) or records an approved plan by `system:automatic-sync` (`AUTOMATIC_PLAN_APPROVED`) and an `APPLY_PREVIEW` with key `automatic-apply:<jobId>`, which `assertJobConsent` rechecks under a row lock before writing.

Consents are also revoked by pause, activation, policy save, mapping change, disconnect, uninstall and scope change, in the transaction that makes the change; these `AUTOMATIC_CONSENT_REVOKED` rows carry `details.reason` (`POLICY_PAUSED`, `POLICY_ACTIVATED`, `CONFIGURATION_CHANGED`, `STORES_DISCONNECTED`, `APP_UNINSTALLED`, `SCOPES_CHANGED`). Rows from `revokeAutomaticConsent` do not.

## Stock pools

Implemented in `app/services/stock-ledger.server.ts`. All writes are owner-only, need an active verified pair and run serializably. `adjust`, `allocate`, `reserve` and `complete` also require `expectedVersion` to equal the pool's version (`STALE_STOCK_POOL` otherwise) and are idempotent per `operationKey` (reuse with a different request: `IDEMPOTENCY_MISMATCH`). `createStockPool` takes neither; a repeated `reference` in the workspace is rejected by its unique constraint (`STOCK_IDENTITY_USED`). Allocations and reservations must conserve stock: total allowances cannot exceed physical minus reserved minus safety buffer (`STOCK_OVERCOMMITTED`). An allowance needs an imported, tracked inventory item at an active location of a workspace store, and an inventory item/location belongs to at most one pool. `completeStockReservation` with `FULFILLED` reduces physical stock; `RELEASED` returns units to the allowance. Each change writes a `STOCK_*` audit event. None of this reads or writes Shopify quantities or orders.

## Jobs, conflicts and reconciliation

`retryJob(actor, jobId)` permits known failed read work. Write jobs cannot be replayed from an old approval; create a fresh preview instead. `cancelJob` revokes an associated approval and marks work cancelled. A Shopify request already submitted can still complete; inspect its live outcome before any repair.

`resolveConflict(actor, {id, resolution: "KEEP_TARGET" | "RETRY"})` records a reviewed decision. `RETRY` means request a new comparison after fixing the cause, not force an old mutation. The UI explains the follow-up import/preview action.

`requestReconciliation(actor, policyId)` creates a durable `RECONCILE` job and run; owners and `OPERATOR` staff may call it. Reconciliation reads current state and records findings; drift produces a pending exact plan for review. Webhooks and scheduled comparisons produce proposals, not unattended writes.

## Preferences and read bounds

`updateSettings` accepts optional workspace name (1–100 characters), reconciliation interval (5–10,080 minutes), retention target (7–3,650 days), `retentionEnabled`, `notificationsEnabled`, `externalNotificationsEnabled`, failure threshold (1–100), and queue-lag threshold (1–1,440 minutes). An owner must opt in to retention and external delivery. External enablement also requires an operator-configured valid HTTPS destination/host allowlist. See NOTIFICATIONS.md for the bounded durable outbox contract.

Mappings and imported suggestions support kind/search filters and independent 25-row pages. Activity, plans, receipts, conflicts, reconciliation runs and audit history also paginate; filtering occurs in the database before paging. Legacy detail IDs remain tenant scoped. Policy configuration selectors remain bounded at 50 policies and 20 recent previews; staff lists are capped at 100. Catalog discovery independently paginates the complete Shopify catalog.

## Webhooks and probes

Configured product/inventory webhook routes call `authenticate.webhook(request)` before receipt persistence, then consume the shop's catalog budget. Delivery IDs are required and unique per shop. The durable inbox/outbox flow creates idempotent worker jobs. Verified uninstall clears sessions and revokes the pair/workspace and automatic consents (reason `APP_UNINSTALLED`, actor `shopify:webhook`) even when a session is already absent; scope-change handling updates scope metadata, revokes automatic consents (reason `SCOPES_CHANGED`), pauses policies, revokes plans and cancels `APPLY_PREVIEW` and `AUTO_PREVIEW` work. Test these lifecycle paths with real development-store events before release.

`POST /webhooks/privacy` authenticates Shopify HMAC before persisting a deduplicated receipt without customer payloads. Customer requests complete with the no-customer-data outcome. Shop redaction is processed after uninstall; a changed/reinstalled connection is held for review. Erasure removes that store's private data and shared workspace state while preserving another store's private catalog and sessions. `GET /privacy` describes data handling.

`GET /health` returns `ok` and reports process liveness only. `GET /ready` checks the database, that the PostgreSQL session `TimeZone` is UTC, and configured Redis, and returns `{"status":"ready"}` or a generic 503 `{"status":"unavailable"}`; it exposes no credentials, dependency addresses, database name or zone. A non-UTC zone is logged as `DATABASE_TIME_ZONE_NOT_UTC` at most once a minute. Neither probe establishes two-store Shopify connectivity or release readiness.

## Verification

`tests/control-plane-guards.test.ts` checks domain/GID validation, challenge security, owner authority, write switches and preview guards. `tests/authorization.test.ts` covers operator capability and the unpaired-staff read-only pages; `tests/rate-limit.test.ts`, `tests/database-clock.test.ts`, `tests/automation.test.ts` and `tests/automatic-sync-route.test.ts` cover request budgets, the time-zone guard, consent scheduling and the automatic-sync loader, actions, page states and grant-limit parity (with the service or the Prisma client mocked). `tests/stock-ledger.test.ts` covers only the stock conservation domain logic; no test calls the stock-ledger service. `tests/integration/control-plane.test.ts` exercises real disposable PostgreSQL transactions for pairing, attempts, expiry, replay, third-store isolation, staff membership, mapping collisions, ownership conflicts, approval consumption/concurrency, invalidation and disconnect; `access-limits`, `automatic-sync` and `database-clock` integration files cover limits, consent grant/scheduling/revocation and the zone guard against PostgreSQL. No test covers a successful automatic run, the in-run budget/scope hold or a consent-bound write through the sync engine. Run through `npm run test:integration`; it creates and drops only a generated local test database.
